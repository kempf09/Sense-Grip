# Slip-detector analysis and tuning (runbook)

Offline pipeline for the phase-4b slip detector (spec
`docs/superpowers/specs/2026-11-17-phase4b-slip-detection-design.md` §4, §7). It reads the recordings
made with `docs/RECORDING_PROTOCOL.md`, replays them through the detector with many parameter sets,
scores the events against the operator marks, picks parameters, and writes a report, plots and a
config patch for the firmware.

> **Synthetic results are plumbing tests only.** `--synthetic` data is generated by
> `make_synthetic.py`; it shows that the pipeline works end to end. Never apply its parameters to the
> gripper and never quote them as tuned thresholds. Only recordings from the real gripper tune anything.

## Setup (once)

```bash
pip install -r tools/requirements.txt         # numpy, pandas, matplotlib (python >= 3.10)
make -C tools/slip_replay                     # the C++ replay tool (same slip_core.cpp as the firmware)
# CI: .github/workflows/analysis.yml runs the two lines above + the tests on every push
python3 tools/analysis/test_pipeline.py       # ~1 min; must end with ALL TESTS PASSED
```

`test_pipeline.py` also checks that the C++ tool and the Python stand-in produce identical slip events
on the synthetic set (skipped with a message if the tool is not built).

## When the real data arrives

1. Unzip everything into one folder (main `.csv` files, `_tof.csv` files and the notes file):
   ```bash
   mkdir -p ~/sg_data/session1 && unzip recordings.zip -d ~/sg_data/session1
   ```
   The notes file is any `.csv`/`.txt` whose first line starts with `file,object` (or pass
   `--notes <file>` to `tune_slip.py`). Make sure the `object` names are consistent (`mug`, not `Mug cup`);
   recordings without a notes line get the class from the file name as their object.
2. Run the whole pipeline (tune → plots → report):
   ```bash
   tools/analysis/run_pipeline.sh ~/sg_data/session1 ~/sg_data/session1_out
   ```
   ~1–2 min for 60 recordings with the C++ tool on 4 cores. Limits are options:
   ```bash
   tools/analysis/run_pipeline.sh ~/sg_data/session1 ~/sg_data/out --max-fa-per-min 0.5 --max-dist-frac 0.3
   ```
3. Read `report.md` top to bottom (see below), look at the plots of every missed slip and every false
   alarm, then decide. The pipeline proposes; the operator decides.
4. Apply the parameters (see *Applying config_patch.txt*), record a few check grasps (quiet hold + pulls)
   and run the pipeline on those as a validation set: the firmware-logged `slip:` events must match the
   replay (report section *Firmware-logged slip events vs replay*).

Individual steps:

```bash
python3 tools/analysis/tune_slip.py --data DIR --out OUT [--replay auto|python|"<cmd>"] [--workers N]
python3 tools/analysis/plot_recording.py --data DIR --out OUT/plots --params OUT/best_params.json
python3 tools/analysis/make_synthetic.py DIR [--seed 1]
tools/analysis/run_pipeline.sh --synthetic [OUT]          # generate into a temp dir and run everything
```

### Which replay is used

`--replay auto` (default) uses `tools/slip_replay/slip_replay` if it is built, otherwise the Python
stand-in `replay_py.py` in-process. The report states which one ran (section *Data*, "Replay:").
Tune with the C++ tool for real decisions: it links the firmware's `slip_core.cpp`, so its numbers are
the firmware's numbers. `--replay python` forces the in-process stand-in; `--replay "<command>"` runs
any program with the same contract (e.g. `"python3 tools/analysis/replay_py.py"`; this one is slow,
~0.4 s per replay, too slow for the full grid; use it only for cross-checks).

## Outputs (`OUT/`)

| File | What it is |
|---|---|
| `report.md` | data summary, chosen parameters vs defaults, overall / per object / per slip type metrics, leave-one-object-out, top parameter sets, best set per fusion mode, per-recording table with plot links, data warnings, firmware-logged vs replayed events, unscorable episodes |
| `best_params.json` | chosen parameters (all 14), what changed vs the defaults, whether the limits are met, all metrics, per object, per slip type, leave-one-object-out folds |
| `config_patch.txt` | `slipXxx=value` lines for the GripConfig fields (`slip` + capitalised parameter name); `#` lines are comments and carry warnings (synthetic data, limits not met) |
| `results_all_sets.csv` | every evaluated parameter set with its overall metrics, best first |
| `plots/<recording>.png` | (a) filtered forces f1..f6 with FSM states shaded, marks and events as vertical lines, (b) raw vs filtered for the pad with the highest force, (c) servo position, (d) width/range/height and rad1..3, (e) replay features `fsr_drop` and `tof_zones` with their thresholds, episode windows and replay slip events (black), firmware-logged slip events (purple dashed) |
| `plots/overview_<object>.png` | one row per recording of the object; both features as a multiple of their threshold (1 = flag) |

### How to read the metrics

* **Episodes** (from the marks): slip = `mark:pull|twist|slide` until the next `mark:end` (else +3 s,
  cut at the next start mark); disturbance = `mark:other` until `end` (else +2 s). An episode counts as
  *detected* / *with event* when a replay slip event falls in `[mark − 0.5 s, end + 0.5 s]`
  (`--tol`). Marks are pressed late, so **negative latency is normal**.
* **Quiet false alarms**: events while the detector is armed (MONITOR after settle) outside every
  episode window, per minute of such quiet time.
* **Not scorable**: a mark outside MONITOR. Recordings with no MONITOR at all (manual recordings,
  jogged in IDLE) are *not replayable*: listed, plotted, never counted as misses. The report also replays
  them with `--force-active` (detector active from the first row where a pad force ≥ `fsrMinForceN`,
  whatever the state) in a separate *Forced active* table that is not part of the tuning metrics.
* **FA ≤10 s after a slip**: quiet false alarms shortly after a slip episode. The detector re-baselines
  when the holdoff after an event ends (forces, frame, object measurement), so an object resting in its
  new place does not re-fire; what remains is motion after the re-baseline (object settling back, the
  operator letting go late after `E`). A large number here says `holdoffMs` (the re-baseline delay) is
  shorter than the typical end of a slip.
* **Leave-one-object-out**: parameters chosen on all other objects (with their own shortlist), then
  evaluated on the held-out object. A wide spread means the thresholds do not transfer between
  objects; the spec requires object-independent thresholds, so this is the number to watch.

### Search grid and selection rule

Staged so the replay tool does all the work (no detector logic in the tuner):

* A, FSR only (mode 0): `fsrDropFrac` {0.2, 0.25, 0.3, 0.4, 0.5, 0.6} × `fsrWindowMs` {150, 300, 500}
  × `fsrConfirmMs` {0, 30, 60} × `fsrMinForceN` {0.15, 0.3}: 108 sets.
* B, ToF only (mode 1): `tofZoneMm` {8, 12, 20, 30} × `tofZoneCount` {2, 4, 6, 10} ×
  `tofConfirmMs` {0, 150, 300, 500}, plus `tofDispMm` {10, 20} at the default zone settings: 66 sets.
* C, fusion: for each context (all data, and each leave-one-object-out training set), the 3 best and
  the most sensitive (false alarms ≤ 4× the limit) sets of A and of B, crossed with mode 2 (either) and
  mode 3 (both) × `fuseWindowMs` {300, 600, 1000}: ≤ 64 sets per context.
* The defaults are always a candidate. Fixed: `settleMs`, `holdoffMs`, `tofNearMm`, `tofZoneFrac`
  (designer's calls, spec §8). Edit `FULL_GRID` in `tune_slip.py` to change the grid. The report flags
  a chosen value at the edge of the grid.

Selection: maximise the slip detection rate subject to quiet false alarms ≤ `--max-fa-per-min` (0.5)
and disturbances with an event ≤ `--max-dist-frac` (0.30); ties → lower mean latency (in bins of
`--latency-tie-ms`, 20 ms = 2 rows, so noise-level latency differences don't decide), then fewer false
alarms. If nothing meets the limits, the set closest to them is reported with a warning.

## Applying config_patch.txt

The lines are GripConfig field names, so either

* type the values into the SEN0628 tab → *Slip detection* fields and save, or
* post them to the gripper's config API (IDLE, dashboard closed or idle):
  ```bash
  curl -X POST "http://<gripper-ip>/api/config" --data "$(grep -v '^#' OUT/config_patch.txt | paste -sd'&' -)"
  ```
  (written from `handleConfigPost` in `SenseGrip/web.cpp`, not yet tried on the gripper.)

Then reload the dashboard and check the SEN0628 tab shows the new values. New recordings carry the
settings in their `# slip:` comment line, and the report compares them.

## Data handling (sgdata.py)

* Comment lines (`#`) anywhere are skipped; `# slip: slipXxx=v,...` is parsed (detector settings at
  recording time; replayed with those settings for the logged-vs-replay check).
* Empty fields become NaN; truncated / garbled lines (wrong field count) are dropped and reported.
* Gaps (seq jumps) are counted and reported; a missing `_tof.csv` means the ToF feature cannot fire
  for that recording (reported).
* Frame records are fed to the detector at main row seq S = every record with `row_seq <= S`.
